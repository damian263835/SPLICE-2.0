Instructions

The S.P.L.I.C.E. script  is a precision instrument, not a bulk scanning utility. Due to the computational load of processing multi-threaded Dense Optical Flow and Kalman matrices, the script cannot process full-length, multi-hour videos. Before using this engine, you must first use preliminary manual methodologies, such as jolt cracking or manual frame-stepping, to  identify the approximate timey of the suspected cut. Once that rough timestamp is found, those specific coordinates must be put into the ⁠START_TIME⁠ variable to allow S.P.L.I.C.E. to run the verification.
Run this code only in Google Colab or else it will not work. Indeed this code was designed for Google Collab because Google Collab already has multiple pre-installed libraries: this prevents the code from being dozens of thousands of lines of code. 
When the S.P.L.I.C.E. script calls ⁠cv2.calcOpticalFlowFarneback⁠ or initializes ⁠cv2.KalmanFilter⁠, it isn't executing Python, but rather triggering tens of thousands of lines of hyper-optimized C++ code from the OpenCV library, which was originally developed by Intel for real-time computer vision. The same principle applies to ⁠skimage⁠ calculating the SSIM micro-fractures and ⁠numpy⁠ handling the underlying mathematics.
If I had to write the base code for a Kalman filter or the tensor array logic for optical flow from scratch in Python, this script would exceed 15,000 lines and run so slowly it would freeze one’s CPU. By outsourcing the brute-force calculations to established C++ libraries, this script keeps the code lean, readable, and incredibly fast.
Regarding Part 1, the script uses an open-source utility called ⁠yt-dlp⁠ to take the footage. It pulls the video data directly from YouTube's servers using the ⁠TARGET_URL⁠ defined. By passing the start time and duration to ⁠yt-dlp⁠, the script forces YouTube to provider only the specific chunk, preventing one  from having to download a massive, multi-hour video file just to analyze a single cut.
Moreover ⁠yt-dlp⁠ is not pre-installed in standard Colab environments.
This is why before you run the main S.P.L.I.C.E. script, you must run the code block titled Part 1  at the very top of your Colab notebook. Do not combine them. First, run Part 1. Once it has successfully run, then run Part 2 so as to download the necessary external tools.

Thresholds and disabling

The S.P.L.I.C.E. script uses high-sensitivity computer algorithms for forensic video analysis. Video compression protocols, such as variable bitrate encoding, alongside high-entropy visual environments, can produce pixel-level artifacts that mimic structural video edits. Consequently, the main code engine requires calibration tailored to the specific parameters of the targeted segment to mitigate false positives and maintain an accuracy rate between 90 and 95 percent.
The Structural Similarity (SSIM) threshold tells the permissible deviation in overall pixel structure between consecutive frames before the engine identifies a micro-compression fracture, which is indicative of a render cut. Calibration of this parameter is necessary if the execution log registers excessive SSIM warnings during rapid camera translations or standard compression artifacting. The threshold is modified by adjusting the execution condition within the SSIMIntegrityScanner class. For raw or lossless local video files, a strict threshold of 0.96 is required. High-quality web video formats warrant a balanced threshold of 0.85. For heavily compressed video streams, lowering the threshold to 0.70 eliminates standard compression noise, isolating legitimate render-stitches which typically manifest at evaluation scores between 0.10 and 0.20.
The Kalman Kinematic Tracker evaluates the physical translation of entities across frames, measuring the distance in pixels to identify anomalous spatial discontinuities mathematically classified as teleportation. Threshold adjustment is required when rapid perspective shifts, sudden field-of-view modifications, or standard entity generation animations trigger false kinematic violations. The threshold is configured by modifying the distance parameters within the KineticEntityTracker class. A baseline distance of 120.0 pixels is optimal for slow-paced visual data to detect minor positional skips. Analyzing high-velocity environments necessitates elevating the threshold to a range of 350.0 to 400.0 pixels, which accommodates rapid animation cycles while successfully flagging absolute geometric anomalies.
The Furnace GUI Chrono-Scanner functions by isolating the center of the frame and measuring the pixel-width of specific graphical user interface elements to verify adherence to 200-tick game mechanics. This module must only be activated when the targeted video segment features an open interface menu. During open-world navigation, the module must be disabled to prevent the scanner from erroneously interpreting center-screen block placements, crosshair movements, or tool animations as fractured interface elements. Deactivation is achieved by commenting out the furnace event execution line within the run_algorithmic_scan method.

Output and Interpretation 

Upon finishing the scan, the S.P.L.I.C.E. engine generates a directory designated as forensic_output inside Colab, which contains the data necessary to verify whether a cut has been made or not. Do not rely on the code’s data solely to determine whether a cut has been made or not. While it may provide strong evidence in favour of a cut, it must be supplemented with human verification and other methodologies, as the risk of false positives remains.
The main output is _ledger.csv, a spreadsheet documenting every issues detected by the engine. This file records the timestamp of the error, the category of the anomaly, the numerical deviation, and the confidence interval, which you can use  as the readable evidence for the investigation.
In addition to the spreadsheet, the engine outputs _report.json. This file contains the identical forensic events formatted as a standardized data export, which is required for integration into secondary data visualization tools or external databases.
The final generated file is _execution.log. This document is a raw diagnostic log confirming the operational integrity of the algorithms during the scan. It provides proof that the multi-threaded processes executed without memory failures or OpenCV assertion errors, ensuring the exported results remain forensically valid.
When reviewing these ledgers, a confirmed splice is seen by simultaneous mathematical anomalies. While an isolated error could be attributed to major video compression artifacts when exporting the video form YouTube’s data center, the presence of concurrent anomalies provides supplementary proof, but not conclusive ones unless seconded by other methods. The  ledger records an SSIM fracture at the timestamp that the furnace clock increments beyond mechanical limits and an entity violates its predicted spatial coordinates, the timeline manipulation is proven.
The resulting CSV or JSON files can be processed through an artificial intelligence model to map the data, summarize timestamps, or generate visualizations. However, such analytical outputs must not be accepted as final proof. Artificial intelligence models are susceptible to hallucinations and may misinterpret spreadsheet rows, fabricate correlations, or omit critical data points. It is necessary to manually cross-reference the model's summary against the raw numerical data within the _ledger.csv to ensure absolute accuracy prior to finalizing the documentation. When using LLM’s, use one of the highest models available so as to reduce hallucinations and errors.

Errors

If the Google Colab environment returns a runtime disconnection or a timeout error, the connection between the browser window and the cloud computing server has been disrupted. This disruption stops the thread executor. To fix this state, you will need to restart the runtime environment and a re-execution of both the installation block and the main S.P.L.I.C.E. engine script.
Should the console output come back as a failure during the extraction phase, the engine is l unable to retrieve the target video data. This error typically comes from an invalid variable within the TARGET_URL, a private or restricted video state on the host server, or a failure to execute the yt-dlp dependency installation prior to initializing the main code. Verification of the URL syntax and the re-installation of the designated libraries is a necessary action.
Instances where the Google Colab runtime crashes or issues an "Out of Memory" exception indicate that the SCAN_DURATION variable exceeds the given hardware constraints of the machine. The simultaneous multi-threaded processing of Farneback Dense Optical Flow arrays and Kalman transition matrices requires substantial dynamic memory allocation. Reducing the SCAN_DURATION parameter to the recommended twenty-second threshold resolves this capacity limitation without compromising the forensic window. If you still get this error, reduce the time threshold, though this may increase the chance of false positives.
While the C++ matrices are typed to prevent data corruption, an OpenCV error concerning dimensional mismatches or data types may still occur if the concerned video segment is inaccessible or contains no readable frames. This exception requires checking the START_TIME variable to ensure the extraction coordinate corresponds to a valid, existing time within the media file.
If the execution log concludes its sequence but the resulting CSV and JSON ledgers contain zero documented events, the engine has worked correctly but detected no issues within the parameters. If a timeline anomaly is expected, this blank output indicates that the START_TIME and SCAN_DURATION variables were calibrated to the wrong sequence, causing the engine to analyze a benign segment of the timeline. A recalibration of the timestamp parameters is required prior to starting a second pass.
Regarding data compression
YouTube standardizes uploaded media by capping playback at a maximum of sixty frames per second. When original footage is recorded at a higher frame rate, the hosting platform discards the excess frames to meet this cap. This frame reduction creates slight visual stutters that mimic a dropped input. The tracking algorithms calculate spatial velocity across the existing frames rather than relying on a frame count. This ensures standard frame reduction is not misidentified as a manual timeline splice.
To conserve bandwidth, the platform applies data compression that groups adjacent pixels into continuous blocks. High-kinetic movement causes these pixel blocks to smear, creating compression artifacts. Basic analytical software frequently misinterprets these artifacts as modified footage. The engine mitigates this by applying adaptive Gaussian thresholding and similarity scans to the static user interface. These methods measure the geometry of the boundaries, ensuring the script identifies actual file stitching rather than standard pixel degradation.
